# Suivi personnel : correction de la perte avant navigation

## Échec constaté

Le workflow `Hessflix verification`, exécution `40725422449`, échouait dans `pnpm test`. L'installation figée des dépendances, la garde de publication, les tests spécifiques et les 127 tests serveur avaient réussi. Parmi les 102 tests navigateur, deux échouaient : les compteurs « En cours » et « Visionnés » affichaient 0 après un clic puis une navigation, au lieu de 1. Les tests de règles étaient alors ignorés parce que l'étape précédente avait échoué.

Les logs complets ont été téléchargés et examinés localement dans un dossier exclu de Git. Les avertissements de dépréciation `url.parse()` et `punycode` n'étaient pas la cause de l'échec. Le workflow GitHub Pages est distinct : une construction statique réussie ne valide pas les tests de l'application et n'exécute pas le serveur Node.

## Cause

`personal-sync.js` attendait `navigator.locks.request()` avant de persister l'action dans son journal local. La demande de verrou est asynchrone. Une navigation immédiatement après le clic pouvait détruire le document avant l'exécution du callback, donc avant toute sauvegarde. Le comportement dépendait du rythme du navigateur et du système ; il ne suffisait pas d'augmenter le délai d'attente du test suivant.

Deux tests ajoutés, avec un verrou volontairement retardé et une navigation immédiate, ont reproduit la perte localement avant correction. [Comportement de l'API Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/LockManager/request).

## Correction

- Chaque action validée possède une intention indépendante, enregistrée synchroniquement dans le stockage local avant le premier `await`.
- La clé est limitée à l'UID, au profil et à un UUID d'action ; des onglets ne réécrivent pas un même tableau partagé en dehors du verrou.
- Le verrou exclusif continue de protéger l'intégration dans le journal numéroté. Le format des opérations envoyées au serveur et les contrôles d'autorisation restent inchangés.
- Les intentions sont récupérées à l'ouverture du profil et avant la synchronisation. Une entrée d'un autre compte ou profil n'est pas importée.
- Un reçu dans le journal empêche de réappliquer une action déjà enregistrée si la page se ferme avant le nettoyage de l'intention.
- Si l'écriture du journal échoue, l'intention persistante n'est pas supprimée. Les limites, avertissements de stockage indisponible, refus terminaux et reprises explicites restent présents.
- Les anciens journaux sans reçus restent lisibles. Les entrées illisibles sont conservées et signalées, sans import automatique.

## Vérifications ajoutées

1. Clic « À reprendre », navigation avant acquisition du verrou, puis rechargement.
2. Même scénario pour « Marquer comme vu ».
3. Interruption du nettoyage après enregistrement : l'action n'est envoyée qu'une fois.
4. Échec d'écriture du journal : intention conservée puis récupérée au rechargement.
5. Deux onglets agissent simultanément ; les deux choix survivent et l'intention d'un autre compte reste intacte.

Les nouvelles vérifications, les deux parcours initialement en échec et les tests existants de reprise ont réussi localement. Les neuf tests des moteurs de règles Firestore, Storage et Realtime Database ont également réussi sur le projet d'émulation `demo-movix-admin`, avec Java 21 portable dans un dossier privé exclu de Git. Aucun service ou donnée de production n'a été utilisé ou modifié ; le Java système est resté inchangé.

Aucun test n'a été retiré, aucune assertion affaiblie et aucune protection ou règle Firebase désactivée. Aucun changement de dépendances ni du workflow CI n'était nécessaire pour cette correction. Le manifeste de publication est actualisé avec les fichiers corrigés et ce document. Le résultat du nouveau workflow GitHub doit être vérifié séparément après le push.
